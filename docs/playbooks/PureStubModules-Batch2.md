# Pure-Stub / Anemic Modules Playbook — Batch 2 (7 modules)

Phase 4 domain-modernization pass, thirteenth module batch. Status as of 2026-08-02.

## Scope: two aggregate-root-from-scratch designs, one simple stub, four literal-empty stubs

Following on from Batch 1's 11 pure-stub modules, this batch covers the remaining stub-module survey candidates minus `CrossDomain` (deliberately excluded — see below): `EnterpriseFabric`, `Financials`, `PlanningProjects`, and all 4 `Intelligence` sub-modules (`AIInvestigations`, `AITraining`, `DataLake`, `PredictiveSafety`).

This batch was more design-intensive than Batch 1:

- **`EnterpriseFabric`** — identical bare-stub shape to Batch 1's 11 modules (Id/CreatedAtUtc/CreatedBy only, no TenantId/SiteId). Straightforward.
- **`Financials`, `PlanningProjects`** — a step barer still: no aggregate root at all, only a child entity (`FinancialLineItem`, `ProjectMilestone`), an empty domain service, an empty specification placeholder, and a pre-existing, fully-documented status enum (`FinancialStatus`, `ProjectStatus`) with no aggregate to attach it to. Required designing genuinely new aggregate roots (`FinancialRecord`, `Project`) from scratch that own the pre-existing child entities.
- **`Intelligence.{AIInvestigations,AITraining,DataLake,PredictiveSafety}`** — literal empty placeholder stubs (`public static class <Module>ModuleMarker { }`), same as `ContinuousImprovement.RCA` was before its own pass. Each had a pre-existing, well-documented read-only DTO (from an earlier, unrelated build pass) that supplied the exact status vocabulary and field shape to ground the new aggregate design in.

**`CrossDomain` was deliberately excluded from this batch and flagged for a user decision.** It has no aggregate roots at all — only cross-system reference/projection DTOs (`EmployeesReference`, `MachinesReference`, `OperatorsReference`, `WorkCentersReference`, etc.) with read-only `Get*Query` handlers per sub-area. This looks like a genuine cross-cutting reference/lookup layer over other bounded contexts' data, not a domain aggregate with its own lifecycle — forcing a lifecycle-modernization design onto it would likely be a category error rather than a legitimate gap.

## Pre-flight audit: live "Features" and "same-concept" verticals hiding under matching names

Before designing, the actual DI-registration state of all 7 candidate modules was checked directly (grep against `InfrastructureServiceRegistration.cs`), extending the discipline established in Batch 1's pre-flight audit:

- **`EnterpriseFabric`**: an unrelated LIVE User-administration vertical (`Application.Features.EnterpriseFabric.Handlers.Users.IUserRepository` → `UserDapperRepository`) shares the module name. Untouched.
- **`Financials`**: an unrelated LIVE Budget-tracking vertical (`IBudgetRepository` → `BudgetDapperRepository`) shares the name. Untouched. **Additionally**, unlike every module audited so far, `Financials` also has a genuinely-related pre-existing READ-ONLY query for the exact same concept (`FinancialsRepository`/`FinancialsReadModel`, `usp_Financial_GetById`, feeding `GetFinancialsQueryHandler`) — this was left completely untouched, with a new parallel by-id write path built alongside it (the `ContinuousImprovement.RCA` "leave the read stack, build a parallel path" pattern, now applied a second time).
- **`PlanningProjects`**: same dual pattern — an unrelated LIVE generic-Project-tracking vertical (`IProjectRepository` → `ProjectDapperRepository`), plus a genuinely-related pre-existing read-only list query (`PlanningProjectsRepository`/`PlanningProjectsReadModel`, `usp_Project_GetById`/`usp_Project_GetAll`) left untouched, with a new `Project` aggregate and parallel by-id path built alongside using a deliberately distinct `PlanningProject`-prefixed table/proc naming to avoid any ambiguity with the existing `usp_Project_*` procs.
- **`Intelligence.AIInvestigations`**: the pre-existing read-only stack is oddly named `AllInvestigations` in the Application layer (a naming drift from an earlier build pass) despite the Domain module being named `AIInvestigations` — the new write path was built under the Domain-matching `Intelligence.AIInvestigations` Application folder, deliberately not reusing the `AllInvestigations` name, to keep the module's actual identity consistent going forward. The old `AllInvestigations` read stack was left untouched.
- **`AITraining`, `DataLake`, `PredictiveSafety`**: each had a same-named, unrelated-in-scope read-only reporting query stack (a coarser shape without lifecycle columns) — left untouched; new aggregates got their own distinctly-named tables (`AITrainingJob`, `DataLakeActivity`, `PredictiveSafetyAlert`) rather than reusing the existing `AITraining`/`DataLake`/`PredictiveSafety` read tables, since those model a different (reporting) shape.

## Domain models built this pass

- **EnterpriseFabric** (general enterprise-integration/system-connectivity record): `FabricArea`/`SystemReference`/`IntegrationType`/`OwnerUserId`, generic `Created→Active→Completed→Closed→Archived` lifecycle.
- **FinancialRecord** (Financials): grounded exactly in the pre-existing `FinancialStatus` enum (`Draft/Submitted/Approved/Rejected/Closed/Archived`, reused unchanged) and the pre-existing `FinancialsItemDto`'s fields. `Create(Draft) → AddLineItem(same-status, Draft only) → Submit(Draft→Submitted) → Approve(Submitted→Approved) / Reject(Submitted→Rejected) → Close(Approved→Closed) → Archive(Closed or Rejected→Archived)`. Owns the pre-existing `FinancialLineItem` child entity as a real collection for the first time — persisted via a delete-then-reinsert child-table strategy (no existing precedent for child-collection persistence was found elsewhere in the codebase, so this is a new pattern, documented for future reference).
- **Project** (PlanningProjects): grounded in the pre-existing `ProjectStatus` enum (`Planning/Active/OnHold/Completed/Cancelled/Archived`, reused unchanged) and `PlanningProjectItemDto`'s fields. `Create(Planning) → AddMilestone/AchieveMilestone (same-status) → Activate(Planning→Active) → PutOnHold(Active→OnHold) → Resume(OnHold→Active) → Complete(Active→Completed) → Cancel(Planning/Active/OnHold→Cancelled) → Archive(Completed or Cancelled→Archived)`. Owns the pre-existing `ProjectMilestone` child entity (including its existing `Achieve()` method), persisted via the same delete-then-reinsert TVP strategy established for `FinancialRecord`.
- **AIInvestigation**: grounded in `AllInvestigationsItemDto`'s vocabulary ("Open/InProgress/Closed") plus the platform-standard `Archived` terminal state. `Create(Open) → StartReview(Open→InProgress) → Close(InProgress→Closed) → Archive(Closed→Archived)`.
- **AITrainingJob**: grounded in `AITrainingItemDto`'s vocabulary ("Queued/Running/Completed/Failed") plus `Archived`. `Create(Queued) → Start(Queued→Running) → Complete(Running→Completed) / Fail(Running→Failed) → Archive(Completed or Failed→Archived)`.
- **DataLakeActivity**: grounded in `DataLakeItemDto`'s vocabulary ("Ingested/Processing/Curated/Failed") plus `Archived`. `Create(Ingested) → StartProcessing(Ingested→Processing) → Curate(Processing→Curated) / Fail(Processing→Failed) → Archive(Curated or Failed→Archived)`.
- **PredictiveSafetyAlert**: grounded in `PredictiveSafetyItemDto`'s vocabulary ("Active/Acknowledged/Resolved") plus `Archived`. `Create(Active) → Acknowledge(Active→Acknowledged) → Resolve(Acknowledged→Resolved) → Archive(Resolved→Archived)`.

## Execution: three parallel agents, 7 modules, zero net regressions

1. **EnterpriseFabric + Financials** — EnterpriseFabric built exactly like Batch 1's modules. `FinancialRecord` built as a genuinely new aggregate root from a child entity + enum + empty service, with the child-collection persistence pattern noted above.
2. **PlanningProjects + Intelligence.AIInvestigations** — `Project` built the same way as `FinancialRecord`. `AIInvestigation` built from a literal empty stub, correctly disambiguating from the pre-existing `AllInvestigations`-named read stack.
3. **Intelligence.AITraining + DataLake + PredictiveSafety** — all 3 built from literal empty stubs. This agent additively extended the shared `StoredProcedureBuilder` (`PlantSafety.Infrastructure\Persistence\Dapper\SqlBuilder\StoredProcedureBuilder.cs`) with `AddLong`/`AddDouble` overloads, since no BIGINT/FLOAT parameter helpers existed yet — a small, legitimate additive extension of a foundational shared class rather than a workaround, now available for any future module needing those SQL types.

A minor, harmless naming inconsistency survives from concurrent execution: agent 2's `AIInvestigation` write repository passes `AiConfidenceScore` (a `double`) through `AddDecimal` with an explicit cast, written before agent 3 added `AddDouble` to the shared builder in a sibling module. Functionally correct (no precision loss for a 0–1 confidence score), just not using the now-available `AddDouble` helper — a cosmetic nit, not fixed this pass.

All three agents' `InfrastructureServiceRegistration.cs` and `GlobalUsing.cs` edits integrated cleanly — `GlobalUsing.cs` had grown to 1358 lines by the time the third agent landed its edits, appended cleanly at the end with no lost sibling entries.

Same recurring naming-collision workaround as needed: `EnterpriseFabric`'s aggregate class name equals its own namespace segment, resolved via `EnterpriseFabricAggregateDapperRepository` naming as usual. `FinancialRecord`, `Project`, `AIInvestigation`, `AITrainingJob`, `DataLakeActivity`, `PredictiveSafetyAlert` all have aggregate names distinct from their enclosing module namespace segment, so no collision workaround was needed for those.

## Known remaining gaps

- No fresh ETag returned on lifecycle-command results across any of the 7 modules (same open item as every prior module).
- No `PlantSafety.DataIntegrationTests`/live-SQL-Server coverage for any of the newly built write paths, including the new child-collection (line-item/milestone) persistence pattern, which has no precedent elsewhere in the codebase and would benefit from real-database verification.
- `CrossDomain` remains unaddressed — genuinely different in shape from every other module tackled in this effort (no aggregate roots, only cross-system reference DTOs) and was deliberately not force-fit into the lifecycle pattern. Needs a product/architecture decision on intent before any further work: is it meant to stay a pure read-only projection layer, or does it need its own aggregate roots?
- The `AiConfidenceScore`/`AddDecimal`-vs-`AddDouble` cosmetic inconsistency noted above — low priority, no functional impact.
- The various pre-existing, coarser "reporting" read tables (`AITraining.sql`, `DataLake.sql`, `PredictiveSafety.sql`, `Financials`/`PlanningProjects` read models) now coexist with the new lifecycle-aware write tables under similar names — same "two parallel persistence stacks" situation flagged in Batch 1 for the 6 modules with live Features verticals; no functional conflict today, but worth a future architectural reconciliation pass.
